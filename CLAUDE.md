# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Repository overview

This repo is a collection of independent prototypes, one per folder, almost all of them browser-based. They share no code and no tooling: there is no build system, package manager, dependency manifest, or test suite anywhere in the repo, and no prototype has external dependencies.

- `file-renamer/` — a self-contained, single-file "Batch File Renamer" web app (`index.html` with inline `<style>` and `<script>`).
- `inbox-digests/` — dated inbox digest reports (`YYYY-MM-DD-inbox-digest.html`) plus an `index.html` archive that browses them.
- `F1/` — a race weekend dashboard (`index.html`, `data.json`, `README.md`). Needs a local HTTP server rather than `file://` because it fetches `data.json`.
- `win-monitor/` — a Windows background activity logger (`win-monitor.ps1`, `win-monitor-tray.ps1`, `Register-WinMonitorTask.ps1`, `README.md`) plus a browser-based log viewer (`index-v0.1.html`, versioned rather than named `index.html` — see the win-monitor section below). The only prototype whose primary artifact isn't a browser page — the logger is plain Windows PowerShell, not JS.
- `affinity-scripts/` — JavaScript scripts for Affinity Photo/Designer/Publisher's built-in scripting engine (run from Affinity's Scripts panel, not a browser), one subfolder per script, each with its own README covering install steps and per-script notes.

Treat each folder as its own project. The sections below cover them individually; don't carry conventions from one into another.

## file-renamer

### Development workflow

There is no build/lint/test tooling in this repo. To work on the app:

- Edit `file-renamer/index.html` directly (HTML, CSS, and JS all live in this one file).
- Open the file directly in a browser to try it (e.g. `open file-renamer/index.html` on macOS, or serve it with any static server such as `python3 -m http.server` from the `file-renamer/` directory). A local server is only needed to test drag-and-drop or folder-picker behavior consistently — plain `file://` access works for most manual testing.
- There is no automated test suite. Verify changes manually in a Chromium-based browser (folder selection via `webkitdirectory` is Chromium-only; other browsers only support multi-file selection).
- Click "Load Sample" in the UI to populate a sample dataset for quick manual verification without needing real files.

### Architecture

The app is a client-side rename **planner**, not a renamer. Plain HTML/JS cannot rename files on disk, so the tool builds a rename plan in memory and lets the user export it as either a CSV (for review) or a PowerShell script (`Rename-Item` commands) to actually execute the renames on Windows.

Everything lives in one `<script>` block in `file-renamer/index.html`, structured as a straightforward pipeline:

1. **Ingest records** — Files come from three input paths, all normalized into a common `record` shape (`fileToRecord`, `importPathList`, `loadSample`):
   - Drag-and-drop or file/folder pickers (`addFiles` → `fileToRecord`), which also read embedded media dates.
   - A pasted plain-text/CSV path list (`importPathList`), useful for testing Windows-style paths without native file access.
   - `loadSample`, which seeds the path-list importer with canned CSV rows.
   - All records are pushed into `state.records`.

2. **Read media metadata** (`readMediaDates`) — For dropped/picked files only, the app extracts real capture dates by parsing raw bytes itself (no libraries):
   - JPEG/TIFF: minimal hand-rolled EXIF parser (`readExifDate` → `parseTiffForExifDate` → `findTiffTag`) that walks the JPEG APP1/TIFF/IFD structure to find `DateTimeOriginal` (tag `0x9003`) or fallback `DateTime` (`0x0132`).
   - MP4/MOV/M4V: minimal MP4 box walker (`readMp4CreationDate` → `findMp4Date`) that recurses into `moov`/`trak`/`mdia` atoms to find `mvhd`/`tkhd`/`mdhd` creation timestamps, converting from the MP4 epoch (1904) via `mp4EpochToDate`.

3. **Build the rename plan** (`buildPlan`, triggered by `refresh` on every input change) — Pure function over `state.records` and the current form options (`getOptions`):
   - Sorts records per `sortMode` (`compareRecords`).
   - Assigns sequence numbers/letters (`formatSequence`, `numberToLetters`).
   - Picks the date to use per record based on `dateSource` (`chooseDate`, with precedence: taken → recorded → created → modified when source is `media`).
   - Renders the name pattern (tokens like `{date}`, `{folder}`, `{base}`, `{seq}`, etc.) via `renderPattern` and `getTokenContext`.
   - Cleans up the result (case, separator, invalid characters) via `cleanupName`/`sanitizeFileName`.
   - Detects and resolves collisions by appending a sequence suffix when enabled, otherwise flags status as `conflict`.
   - Produces `state.plan`, an array of `{record, newName, dateUsed, status, ...}` used purely for rendering — nothing is written to disk here.

4. **Render** (`renderStatus`, `renderTable`) — Reflects `state.plan` into the status pills and preview table. All UI state is driven by re-running `refresh()` (`buildPlan` + both render functions) on any input change; there is no incremental diffing.

5. **Export** (`exportCsv`, `exportPowerShell`) — Turns the current `state.plan` into a downloadable file via an in-memory `Blob` and a synthetic `<a download>` click (`downloadText`). The PowerShell export excludes `unchanged`/`conflict` rows and quotes paths/names with `psString` for safe `Rename-Item -LiteralPath` usage.

### Key conventions

- Paths are normalized to forward slashes internally (`splitPath`) regardless of source OS, and converted back to backslashes only when generating the PowerShell script.
- `record.path`/`record.directory`/`record.folder`/`record.base`/`record.ext` are the canonical decomposed-path fields used throughout the pipeline — reuse `splitPath`/`splitName` rather than re-deriving these from a raw path.
- `state.records` is raw input data (immutable per session, only appended/cleared); `state.plan` is always a derived, disposable recomputation from `state.records` + current options — never mutate `state.plan` directly or hand-patch it, just call `refresh()`.
- All user-supplied/file-derived text rendered into the DOM goes through `escapeHtml`; anything written into the generated `.ps1` goes through `psString`. Keep using these when adding new rendered/exported fields.

## F1

A race weekend dashboard: track map with per-sector highlighting, race distance, historic results, tire compounds, pit stop time loss, and a parked placeholder for live timing.

- Serve it over HTTP — `cd F1 && python3 -m http.server` — because it fetches `data.json`. Opening `index.html` over `file://` deliberately renders a "serve over HTTP" message instead of a blank page.
- `F1/data.json` holds the circuit dataset; adding a circuit needs no code changes. `F1/index.html` holds all markup, styles, and logic.
- Historic results are fetched live from the Ergast-compatible API configured under `meta.api` in `data.json`; the seeded `history` arrays are the offline fallback and render until (or instead of) a successful response. A pill above the table always says whether the data is live or sample.
- `F1/README.md` is the detailed reference — data shape, API behaviour, layout, and what is parked. Read it before changing the data layer.

## win-monitor

A Windows background logger that records which window has focus, the file it has open (parsed from the title bar), and how long it held focus — plus every stretch where the machine sat idle or locked, so someone can tell when it was left unattended with windows open.

- `win-monitor/win-monitor.ps1` is the logger: a single PowerShell script, no installed modules, using `Add-Type` for a handful of `user32.dll`/`kernel32.dll` P/Invoke calls (foreground window, window title, last-input time, input-desktop check for lock state). It writes one JSONL + CSV pair per day to `%LOCALAPPDATA%\win-monitor`. `Step-Session` (the idle/active/locked state machine) and `Get-ActiveDocument` (title → file-name heuristics) are the two functions to read first — both are pure enough to unit test by extracting them from the script via `System.Management.Automation.Language.Parser` and calling directly, which is how this prototype was verified (this repo has no test runner, and PowerShell isn't available to run interactively here — see `win-monitor/README.md` for the reasoning behind the idle/lock timing). It exits cleanly (flushing the in-progress session, same as Ctrl+C) when a `-StopFlagPath` file appears — checked once per poll — which is how `win-monitor-tray.ps1` stops a hidden instance it has no console to send Ctrl+C to. It also holds a named `System.Threading.Mutex` (`Global\win-monitor-<sanitized LogDirectory>`) for its whole run and exits immediately (code 1, before touching the filesystem) if it can't acquire it — a second instance against the same `-LogDirectory` used to write genuinely overlapping session entries into the same file (two loggers running at once, e.g. a manual console run left going alongside the tray's hidden instance), which is real data corruption that makes the viewer's Active Time double-count and read over 100%. A mutex, not a lock file, specifically because Windows releases it automatically on crash/kill — no stale-lock cleanup logic needed. `win-monitor-tray.ps1`'s `Start-Monitor` checks `HasExited` ~600ms after launch and surfaces a MessageBox if the child died immediately, since that's the signature of losing this lock. The main loop has a `Write-Verbose` on every poll reporting `idleSeconds`/threshold/locked/state — silent unless `-Verbose` is passed (a free `[CmdletBinding()]` common parameter) — added when idle sessions were reported as never registering on a real (non-VM) Windows 11 machine despite the state machine tracing correctly by hand; `GetLastInputInfo` is systemwide and can't tell real input apart from anything else that synthesizes it (RDP clients, some mouse/keyboard software), so `.\win-monitor.ps1 -DryRun -Verbose` is the fastest way to see whether `idleSeconds` is actually climbing on a given machine before assuming the code is at fault.
- `win-monitor/win-monitor-tray.ps1` is what actually runs in the background day to day: it launches `win-monitor.ps1` as a separate hidden process and shows a system tray icon (drawn at runtime via `System.Drawing`, no `.ico` asset) with Open log folder / Open log viewer / Idle threshold / Minimum active time / Exit. Exit writes the stop-flag file rather than killing the child process, so the current session gets flushed; changing either setting does the same (stop, then relaunch the child with both current values) rather than killing it outright — the two submenus share one `Set-LoggerSettings` restart function rather than duplicating it. Both settings are persisted together to `tray-settings.json` next to the logs (each field falls back independently to its own `-IdleThresholdSeconds`/`-MinSessionSeconds` parameter if missing or corrupt, so a bad value in one doesn't discard a good value in the other) and override those parameters (first-run seeds only) on every future launch — including ones the Scheduled Task starts at logon. `win-monitor.ps1` itself is unchanged by any of this and still runs standalone via `win-monitor.cmd` or a console for foreground testing. `win-monitor-tray.cmd` is the double-click entry point for this script, launched detached (`start`) so no console window lingers, unlike `win-monitor.cmd`.
- The tray's tooltip second line ("Now: app: title") polls the foreground window independently via its own small `WinMonitor.Tray.NativeWindow` P/Invoke class, on a `System.Windows.Forms.Timer` (UI-thread-safe, unlike `System.Threading.Timer`) — deliberately not read back from the logger process, to avoid needing IPC between the two. That means it shows whatever currently has OS focus, not the logger's own idle/locked state; it's a glance, not the record.
- `win-monitor/Register-WinMonitorTask.ps1` registers the per-user Scheduled Task that makes it "run in the background": logon-triggered, hidden window, **Interactive** logon type at **Limited** run level, with `win-monitor-tray.ps1` (not `win-monitor.ps1` directly) as the task's action. Don't change it to "run whether logged on or not" — that executes in Session 0 with no desktop, so `GetForegroundWindow` returns nothing and the log goes empty.
- `win-monitor/index-v0.1.html` is the current viewer; `win-monitor/index-v0.0.html` is the original, unmaintained snapshot kept only for comparison — files are versioned (`index-vX.Y.html`) rather than a single `index.html` so a from-scratch layout rewrite could exist alongside what it replaced. Develop against `index-v0.1.html` (bump the suffix and duplicate rather than editing `index-v0.0.html`); `win-monitor-tray.ps1`'s `$viewerPath` and "Open log viewer" point at `index-v0.1.html`, not `index.html` — keep that path in sync if the current version changes. It is a self-contained, single-file log viewer (same inline `<style>`/`<script>` shape as `file-renamer/index.html`) that reads the JSONL/CSV files the logger writes — via drop, file picker, or paste — and renders a timeline, an away-periods table, time-by-app/file bars, and a sessions table. It has no dependency on the PowerShell side beyond the log format; "Load sample" seeds a two-day example without needing a real log. Project assignment (per-session dropdown in the Sessions table, plus a filter-driven batch-assign and a checkbox-based multi-select with shift-click range selection for an explicit-selection batch-assign) is deliberately *not* stored in the browser — `state.projectAssignments` (keyed by `entryKey(entry)`, the same identity already used for log-row dedup) persists only via an explicit exported/imported `win-monitor-projects.json` sidecar file, `loadFiles`/the paste importer sniff a dropped/pasted file's shape (`{assignments: {...}}`) to route it there instead of the log parser. This is a deliberate choice, not an oversight — don't "fix" it by adding `localStorage` without checking with whoever asked for it first. `#importProjectsBtn` (a hidden `#projectsFileInput` behind it) is the explicit counterpart to `#exportProjectsBtn` — both call the same `loadIfProjectsFile`/`exportProjects` used by the drop zone and paste box, so there's exactly one loading/saving path regardless of entry point. `state.selectedSessionKeys` (checkbox selection) is pruned to the currently-rendered rows on every `renderSessions()` call, so a selection never silently includes something a filter change just hid. Every results panel (`section.collapsible`) has a `.collapse-toggle` button that folds its `.section-body` via a `.collapsed` class — sidebar sections deliberately don't get this, so don't add it there. Collapsing is purely a display:none on the wrapper; `refresh()` keeps re-rendering the content underneath regardless of collapsed state, so nothing goes stale while hidden. "Time by project" (`#projectBars`, computed in `renderBars`) buckets sessions with no assignment under `'Unassigned'` rather than omitting them, so the totals stay complete. The date-range back/forward buttons (`shiftDateRange`) page by the range's *own* length via calendar-date `setDate()` arithmetic (`addDays`), not raw millisecond math, since DST transitions can shift millisecond-based day addition onto the wrong side of local midnight. **Load latest log** (`#loadLatestBtn` → a hidden `#folderInput` with `webkitdirectory`, same folder-picker API `file-renamer` uses, Chromium-only) picks the newest `activity-*.jsonl` out of a picked folder by the date *in the filename* via `findLatestActivityFile`, not `file.lastModified` — the filename is what win-monitor.ps1 considers authoritative for which day a file belongs to, and it's immune to a sync/copy tool touching mtimes. `countOverlappingSessions` (a sort-by-start sweep tracking the running max end seen so far) flags logs written by two concurrent `win-monitor.ps1` instances — a well-formed single-instance log never has overlapping session ranges — and surfaces it as a pill plus a note on the Active Time tile rather than silently showing an impossible over-100% figure; this stays useful even after the logger's own single-instance lock, for logs collected before that fix existed. `.controls` (the sidebar) is deliberately *not* `position: sticky` — it was, until that turned out to cause a real overlap/paint bug on at least one real machine (not reproducible in this environment even at the same data scale); don't re-add it without confirming the underlying rendering issue is understood.
- The file name is inferred from the window title, not read from any API — there is no way to plainly ask Windows what file a window has open. `Get-ActiveDocument` in `win-monitor.ps1` documents the heuristics and their known failure modes (generic titles, browser tabs without a recognized document extension); treat `file` as a strong hint, not ground truth.
- `win-monitor/README.md` is the detailed reference — log format, session types, the poll/last-input timing model, and viewer usage. Read it before changing the logging or parsing logic.

## affinity-scripts

JavaScript scripts for Affinity Photo/Designer/Publisher 3.x's built-in scripting engine — run from Affinity's Scripts panel, not a browser or Node. Each script lives in its own subfolder with its own README; no shared code with the rest of the repo, or between scripts.

- `affinity-scripts/Image Relink/relink-images.js` walks the active document's spreads/layers for linked (not embedded) image nodes, checks each recorded path with `FileSystemApi.exists`, and for anything missing or moved offers a native file picker (`FileSystemApi.getOpenFileName`) to relink it — reusing the folder the user picked for the previous fix before asking again, since moved assets are usually moved together. Writing the corrected path back (`imageResourceInterface.imageFilePath = newPath`) is a best-effort call: the SDK confirms that property as readable (used by community scripts) but its writability isn't documented, so failures are caught per-file and reported rather than aborting the batch — see `affinity-scripts/Image Relink/README.md` for the fallback (Resource Manager > Relink).
- `affinity-scripts/Split Text/split-text-by-words.js` breaks a text frame into one text object per word, by duplicating the frame once per word (so all formatting carries over) and writing a single word into each duplicate, then laying them out in a row/column or leaving them stacked. It works from the selection, falling back to every text frame in the document after warning. Because no published API reference exists for the text/duplicate/move/delete calls (see below), every one of them goes through the `attempt`/`attemptVoid` probing helpers, which try a list of candidate spellings and report the operation by name in the summary dialog when none works — a frame whose words can't be written is abandoned before its duplicates are kept, so nothing is left half-split. `setText` in particular verifies by reading the text back rather than trusting that the assignment didn't throw: several candidate spellings will silently create a new unused property on the node instead, which would leave every duplicate showing the full original sentence while the script reported success. Word spacing uses each duplicate's own bounds *after* its text is replaced (Affinity exposes no text measuring API), falling back to an even split of the original frame's width and, failing that, to stacking with an explicit note in the summary. Don't replace the probing with a single hard-coded spelling unless it's been confirmed against a real build. See `affinity-scripts/Split Text/README.md`.
- The scripting object model (`/application`, `/fs`, `/dialog`, `doc.spreads` → `spread.layers.all`, `node.imageResourceInterface`) was confirmed by reading real community scripts in `JiriKrblich/Affinity-Community-Scripts` (e.g. its RGB Finder and Smart Exporter scripts), not from official reference docs — Affinity's own SDK reference is served locally from within the app (via an MCP server on `localhost:6767`) and isn't published on the web.
